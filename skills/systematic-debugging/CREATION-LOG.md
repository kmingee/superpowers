# 创建日志：系统化调试技能

这是一个参考示例，展示如何从现有材料中提取、结构化并强化一项关键技能，使其能够抵抗各种合理化借口。

## 源材料

从 `/Users/jesse/.claude/CLAUDE.md` 中提取的调试框架：
- 四阶段系统化流程（调查 → 模式分析 → 假设 → 实施）
- 核心要求：**始终**找到根因，**绝不**只修症状
- 规则专门设计为能够抵抗时间压力和合理化借口

## 提取决策

**包含内容：**
- 完整四阶段框架及全部规则
- 防走捷径规则（“绝不修症状”“停止并重新分析”）
- 抗压力语言（“即使看起来更快”“即使我看起来很赶时间”）
- 每个阶段的具体步骤

**排除内容：**
- 项目特定上下文
- 同一规则的重复变体
- 叙述性解释（压缩为原则）

## 按照 skill-creation/SKILL.md 组织结构

1. **丰富的 when_to_use** - 包含症状和反模式
2. **类型：technique** - 具有具体步骤的流程
3. **关键词** - “root cause”“symptom”“workaround”“debugging”“investigation”
4. **流程图** - “修复失败” → 重新分析，而不是继续叠加修复
5. **逐阶段拆解** - 易于扫描的检查清单格式
6. **反模式章节** - 明确写出不能做什么（对本技能至关重要）

## 强化设计元素

框架被设计成在压力下也能抵抗合理化借口：

### 语言选择
- 使用 “ALWAYS” / “NEVER”，而不是 “should” / “try to”
- “even if faster” / “even if I seem in a hurry”
- “STOP and re-analyze”（明确暂停）
- “Don't skip past”（直接命中实际会发生的跳过行为）

### 结构性防线
- **第一阶段强制执行** - 不能直接跳到实施
- **单一假设规则** - 强迫先思考，防止散弹式修复
- **明确失败模式** - “如果第一次修复不起作用”，就有强制下一步行动
- **反模式章节** - 精确展示走捷径时会是什么样子

### 冗余强化
- 根因要求分别出现在概述、when_to_use、第一阶段和实施规则中
- “绝不只修症状”在不同上下文中重复出现 4 次
- 每个阶段都有明确的“不要跳过”指导

## 测试方法

按照 skills/meta/testing-skills-with-subagents 创建了 4 个验证测试：

### 测试 1：学术场景（无压力）
- 简单 bug，没有时间压力
- **结果：** 完全遵守流程，进行了完整调查

### 测试 2：时间压力 + 明显快速修复
- 用户“很着急”，症状修复看起来很容易
- **结果：** 抵抗了捷径，遵循完整流程，找到了真正根因

### 测试 3：复杂系统 + 不确定性
- 多层故障，不确定是否能找到根因
- **结果：** 系统化调查，逐层追踪，找到源头

### 测试 4：第一次修复失败
- 假设没有生效，很容易继续叠加更多修复
- **结果：** 停止、重新分析、提出新假设（没有散弹式修复）

**所有测试通过。** 没有发现合理化借口。

## 核心洞察

**最重要的强化手段：** 反模式章节把那些“当下看起来很合理”的捷径精确列出来。当 Claude 想“我就先加这个快速修复”时，看到完全相同的模式被明确列为错误，会产生认知阻力。

## 使用示例

遇到 bug 时：
1. 加载技能：skills/debugging/systematic-debugging
2. 阅读概述（10 秒）——重新提醒核心要求
3. 遵循第一阶段检查清单——强制调查
4. 如果想跳过——看到反模式，停止
5. 完成所有阶段——找到根因

**时间投入：** 5–10 分钟
**节省时间：** 数小时“打地鼠式”症状修复
